# Supabase: настройка и проверка

Клиент использует только публичные `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
Серверный service-role ключ клиенту не нужен. При отсутствии конфигурации приложение работает локально.
SDK находится за `AuthService` и `SyncTransport`; доменные модели не зависят от Supabase.
Application UUID сохраняется в отдельном несекретном кеше с ключом auth ID. При временной ошибке
сети он используется только для совпадающего пользователя существующей SDK-сессии; HTTP 401/403
не используют кеш. Ошибки подписки передаются через `onError`, сохраняя владельца при временной
ошибке того же аккаунта. При смене auth ID прежний владелец сбрасывается до загрузки нового UUID,
чтобы сессия B не могла продолжить изменения локальных данных аккаунта A.
Недоступность localStorage обрабатывается; в открытом приложении остаётся кеш в памяти.

## Применение

Миграция `supabase/migrations/202611120001_user_sync.sql` подготовлена для нового проекта Supabase.
Она не применялась к live-сервису автоматически. Откройте SQL Editor своего проекта, проверьте проект и
выполните содержимое файла целиком. Для существующей схемы сначала подготовьте резервную копию и
проверьте совместимость: миграция намеренно не скрывает конфликты имён через `IF NOT EXISTS`.
Локально с Supabase CLI можно использовать `supabase db reset`, но только в выделенной тестовой базе:
эта команда удаляет её данные.

В Auth включите Google и GitHub, укажите OAuth callback провайдера из панели Supabase.
Разрешённый redirect приложения: `https://striderajr.github.io/ReadFold/`; для разработки добавьте
локальный origin с текущим Vite base path. Приложение использует HashRouter, поэтому PKCE callback
возвращается в корень base path. SDK обрабатывает `code`, восстанавливает и обновляет сессию.
Не запускайте повторный ручной `exchangeCodeForSession` параллельно автоматической обработке SDK.

## Границы доступа

`app_users.id` — независимый UUID приложения, связанный с `auth.users.id` уникальным
`auth_user_id`. `ensure_app_user()` получает auth ID только из проверенного JWT через `auth.uid()`.
Клиент не передаёт auth ID в RPC. Код приложения не связывает аккаунты по email и не вызывает
`linkIdentity`; правила автоматического связывания провайдеров самого Supabase Auth нужно учитывать
при настройке проекта.

RLS разрешает чтение только своего пользователя и своих операций. Прямые записи для `anon` и
`authenticated` запрещены. RPC записи проверяет владельца по JWT, допустимые виды операций,
формат envelope и размер: до 100 операций / 1 MiB на пакет, до 64 KiB payload на операцию.
Payload каждого вида проверяется по правилам локальной модели: обязательные поля, типы, диапазоны
настроек, допустимые статусы обучения, `favorite.active` и корректные ISO-даты с календарной проверкой.
`deviceId` — ограниченная текстовая метка, а не основание для авторизации; авторизация всегда по JWT.
Содержимое payload не исполняется и не используется для назначения прав.

RPC с `SECURITY DEFINER` используют пустой `search_path` и явно указанные схемы. PUBLIC EXECUTE
отозван; анонимному пользователю доступен только `heartbeat()`, возвращающий `true` без данных.
Встроенные JWT, PKCE verifier и refresh token обслуживает SDK. Любой код того же origin имеет доступ
к браузерному хранилищу сессии: не вставляйте недоверенный HTML и сторонние скрипты без проверки.

## Доставка операций

Сервер хранит все события, включая конкурирующие изменения одного объекта. Повтор `(owner,id)`
с идентичным JSONB безопасен; повтор ID с другим содержимым завершается ошибкой и откатывает пакет.
Удаление ledger из клиента запрещено. Конфликты разрешает локальная доменная модель, а не серверный
timestamp: часы устройства не определяют порядок доставки.

Каждый владелец имеет собственный последовательный cursor. Запись блокирует строку пользователя
до commit и только затем назначает номера. Таким образом, транзакция с большим cursor не может
зафиксироваться раньше меньшего и вызвать пропуск при следующем pull. Pull отдаёт до 100 событий
в порядке cursor и cursor последнего события; при пустой странице сохраняет входной cursor.
Клиент сохраняет полученные события и cursor одной локальной транзакцией. После смены пользователя
нужен отдельный локальный cursor. Диапазон cursor ограничен безопасным целым JavaScript.

Адаптер разбивает исходящий outbox на пакеты до 10 операций и 256 KiB компактного JSON
(с запасом на формат JSONB). Частично отправленный outbox можно безопасно повторить.
Production sync transport вызывает PostgREST через изолированный HTTP-адаптер с действующей сессией SDK,
передавая HTTP-статус и фактический Retry-After механизму повторов. Если 429 не содержит заголовка,
используется запасная задержка 60 секунд. Ошибка конфликтующего ID возвращает 409.

## Проверки

`supabase/tests/user_isolation.sql` — исполняемая SQL-проверка для одноразовой локальной базы после
миграции. Запустите через psql с `ON_ERROR_STOP=1` от postgres. Она создаёт два фиктивных auth ID,
проверяет RLS, RPC-изоляцию, запрет подмены owner, повторов с другим содержимым, прямой записи
и анонимного доступа. Все fixture-записи откатываются. Не запускайте её на live-проекте.
Конкурентное назначение cursor дополнительно проверяется анализом блокировки `FOR UPDATE`;
для нагрузочной проверки нужны отдельные параллельные подключения PostgreSQL.

`npm run test:sql` воспроизводит миграцию и этот тест в локальном PostgreSQL/WASM (PGlite)
с минимальной auth schema. Проверка прошла; она не заменяет проверку реальных настроек Auth и сети.
Удалённая миграция применена с явного разрешения владельца с доверенным CA-сертификатом и проверкой TLS.
Read-only проверка подтвердила RLS двух таблиц, ownership policies, запрет клиентской записи и anonymous private
RPC; heartbeat доступен, anonymous чтение данных получает 401. Fixture-пользователи на live не создавались.
[Документация Supabase о CA](https://supabase.com/docs/guides/platform/ssl-enforcement).
